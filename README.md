# 点态留存分析（Pointwise Retention）

本地运行的双时态（bitemporal）留存分析系统。数据全部为**虚构合成数据**，不进行任何真实用户识别。

## 它解决什么问题

留存分析的原始信号来自三类身份——注册账号、设备、匿名访问——它们会被合并、被拆开，
活动事件还会迟到。因此同一份留存数字存在两个互相冲突的正确版本：

- **当时已知（as-known-then）**：在历史某个版本，系统只能基于当时的身份关系和已到达的事件计算；
- **当前修正（as-corrected-now）**：用今天的合并关系和回补事件重算的结果。

本系统的原则是：**绝不用今天的合并关系冒充当时就知道**。每个写入都追加一个单调递增版本，
事件同时记录「发生时间 `event_time`」和「被系统知道的版本 `ingest_version`」，
身份边用生效区间 `[from_version, to_version)` 表达，因此任意历史版本的报告都可以原样重建，
后续写入不会改变历史报告。

## 快速开始

```bash
# 零外部依赖，仅需 Python 3.11+ 标准库
python3 run.py                 # 自动建库 + 灌入合成数据 + 启动 http://127.0.0.1:8000
python3 run.py --reseed        # 删掉旧库重新生成
python3 -m unittest discover   # 16 个后端测试
```

浏览器打开 <http://127.0.0.1:8000>。

## 三种队列口径与取舍

| 口径 | 队列成员 | 重复计数 | 跨端覆盖 | 适用问题 |
|---|---|---|---|---|
| `entity` 稳定实体 | 身份图连通分量（DSU 根） | 最低 | 最高 | 「真实有多少人在用」；错误合并会低估人数，拆分后部分历史事件无法归属 |
| `account` 注册账号 | 含账号节点的实体，以账号 id 为键 | 低（写入侧禁止一实体多账号） | 高（同账号多设备合并） | 财务/可复算口径；未注册访问被完全排除 |
| `visit` 访问身份 | 每个身份节点独立计数 | 最高（同一人 N 端 = N 个成员） | 零 | 「系统当时看到了多少次访问」；不做任何回溯改写，最贴近埋点原始事实 |

合成数据里同一批信号在三口径下的成员数为 `visit(20) ≥ entity(12) ≥ account(6)`，
差异本身就是口径取舍的可视化证据。

## 拆分与「不确定」事件

撤销合并（split）**只关闭身份边、从不删除节点或事件**。拆分后：

- 带 `emitter_id` 的事件仍可唯一归属（事件本就是那个节点产生的）；
- 无 emitter 的服务端回补事件，若到达时挂载的多个节点如今已分属不同实体，
  则**明确保留为「不确定」，不按比例分摊、不随意挑一个实体**。

留存矩阵中受影响的单元格因此给出**区间而非单值**：

- 下界 = 确认活跃成员数；
- 上界 = 确认活跃 + 该周不确定事件的候选成员（封顶队列人数）。

不确定事件在独立面板和钻取视图中逐条列出（事件 id、挂载节点、候选成员、原因），可导出 CSV。

## 版本一致性：身份裁决 / 事件回补 / 后台重算并行时

- 所有写操作在 `BEGIN IMMEDIATE` 事务 + 进程内写锁中推进版本号，读走独立连接（WAL）。
- 后台重算任务**启动瞬间钉住 `pinned_version`**：队列成员与各周分母全部取自该版本。
- 任务完成时再读一次最新版本：若期间有写入，状态标记为 `stale`，
  产出的快照仍严格停留在钉住版本，并提示需要重跑——绝不把新版本的分母混进旧队列。

## 网页可做的事

1. 切换三种队列口径、切换任意历史版本（顶部徽章区分「当时已知 / 当前修正」）；
2. 点击留存矩阵任意单元格，钻取该队列在该周的确认活跃成员、未活跃成员、不确定事件及候选成员；
3. 版本时间线：任选两个版本做 diff（身份图结构变化、队列成员首活跃周变化、单元格变化）；
4. 操作区：回补事件（可迟到）、身份合并、撤销合并，每个操作追加新版本，历史报告不变；
5. 启动后台重算观察钉版与 stale 检测；保存/查看报告快照；
6. 矩阵与钻取结果均可导出 CSV（带 BOM，Excel 可直接打开）。

## 合成数据场景（确定性，种子固定）

| 场景 | 内容 |
|---|---|
| S1 | 匿名 `anon_7` → 设备 `dev_1` → 注册 `acc_1`，再并入第二台设备 `dev_5`（跨端合并主线） |
| S2 | 普通单设备账号 `acc_2`/`acc_3` 的完整生命周期 |
| S3 | `dev_4` 与 `anon_9` 被错误合并后人工撤销，期间的无 emitter 事件变成不确定 |
| S4 | 迟到事件：`event_time` 在 W0/W1，`ingest_version` 在 W4/W5 才到达 |
| S5 | 永不注册的独立设备/匿名访问（只在 visit 口径出现） |

## 数据模型要点

- `versions`：仅追加的版本日志（`node_birth | edge_open | edge_close | event_ingest`）。
- `id_nodes`：身份节点，`born_version` 表示系统何时知道它。
- `id_edges`：身份边，`from_version`/`to_version` 构成半开生效区间，拆分是更新而非删除。
- `events`：`event_time`（何时发生）与 `ingest_version`（何时被知道）正交；
  `emitter_id` 为空时靠 `attached_ids` 归属，挂载集合跨多个现分量即不确定。
- `report_snapshots` / `recompute_jobs`：报告版本留痕与重算钉版记录。
